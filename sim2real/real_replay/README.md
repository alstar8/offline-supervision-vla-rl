# real_replay

Запуск траекторий, сгенерированных в ManiSkill, на реальном RC5 + AeroHand.

`replay_npz_real.py` — адаптация `rc5_aerohand_teleop/replay_jsonl_real.py` под формат NPZ.
Путь управления железом (jog P-контроллер, E-stop, workspace-клампы) намеренно оставлен
идентичным проверенному оригиналу; отличается только источник траектории.

## Рекомендуемый путь: суставной реплей

Декартов реплей дельт из NPZ (ниже) переносится на железо плохо: фреймы контроллера и URDF
различаются, а целевые дельты при открытом цикле переезжают. Суставный путь обходит обе
проблемы. Сцена — `airy_table_scene14sep26_left_image_metric` (исправленный масштаб).

```bash
# 1. Где реальный объект относительно цели в сцене (только камера, робот не трогается)
python3 real_replay/locate_object_zed.py --object green_cube_ext

# 2. Захват в симуляторе с записью суставов на каждом шаге среды -> <run>/joint_trajectory.npz
make record-joints KEY=airy_table_scene14sep26_left_image_metric TASK_OBJECT=green_cube_ext
#    с окном вьювера: JOINTS_VIEWER=1; точка спуска без подъёма: DESCEND_DZ=0

# 2a. Посмотреть записанную траекторию в симуляторе: записанные суставы и позы объекта, без физики,
#     те же состояния, что уйдут на робота (опции как у реплея: --until-height, --reverse, --speed)
make view-joints TRAJ=runs/manual/<run>/joint_trajectory.npz VIEW_ARGS="--until-height 0.15"
#     клавиши: n — проиграть, SPACE — пауза/шаг, r — в начало, q — выход; без окна: VIEW_ARGS="--video out.mp4"

# 3. Dry-run: план точек, события кисти, развёртка на 360°, расхождение со стартом
/home/aermakov/github/aero-env/bin/python real_replay/replay_joints_real.py <run>/joint_trajectory.npz --dry-run --read-robot

# 4. На железе: сначала зависнуть над объектом и проверить выравнивание по ZED
/home/aermakov/github/aero-env/bin/python real_replay/replay_joints_real.py <run>/joint_trajectory.npz --until-height 0.15

# 5. Вернуться тем же путём (та же высота, что в шаге 4)
/home/aermakov/github/aero-env/bin/python real_replay/replay_joints_real.py <run>/joint_trajectory.npz --until-height 0.15 --reverse

# 6. Полный захват
/home/aermakov/github/aero-env/bin/python real_replay/replay_joints_real.py <run>/joint_trajectory.npz
```

Что важно знать:

- **Суставы пишутся во время прогона planner'а**, а не восстанавливаются из NPZ: в NPZ попадает
  лишь часть шагов среды (для зелёного кубика 246 из 366), и открытое воспроизведение его
  действий захват не повторяет.
- **Суставный реплей принимает только `joint_trajectory.npz` из `make record-joints`.** Обычный
  `make planner` / `planner-headless` суставы не пишет, а его `rl4vla_raw_episode*.npz` содержит лишь часть
  шагов среды — восстановить из него суставы нельзя. На такой файл скрипт откажется ещё до подключения к роботу.
- **`DESCEND_DZ=0.015` по умолчанию.** Со штатной точкой спуска кончики большого пальца и мизинца в симуляции
  проходят в 5–6 мм от стола, а реальная кисть идёт на ~1 см ниже плана. +15 мм дают ~22 мм запаса, и захват
  в симуляции сохраняется. Смещение применяется только к этому прогону и пишется в метаданные траектории.
- **Движение — декартов jog по скорости TCP, как в `replay_npz_real.py`.** Суставный jog RC5 передаёт для
  каждого мотора только направление (−1/0/+1), плавно вести им траекторию нельзя. Поэтому каждое состояние
  траектории переводится в позу TCP прямой кинематикой самого контроллера (`motion.kinematics.get_forward`),
  и TCP ведётся во времени П-регулятором с упреждением по скорости. `--speed` — множитель к темпу симуляции
  (по умолчанию 0.3: на полной команде jog даёт ~5 см/с); dry-run показывает скорость и длительность.
  Начальная выдержка записи пропускается. Перед командой кисти TCP доводится до позы этого шага
  (`--pos-tol`, `--rot-tol-deg`, `--settle-timeout`). Суставы выбирает контроллер, поэтому прогон
  останавливается, если любой сустав уйдёт от записанного пути дальше `--max-joint-dev` (8°) или TCP отстанет
  от цели дальше `--max-track-err` (5 см). `--move-to-start` по-прежнему одно суставное перемещение, не jog.
- **Суставы симулятора равны суставам реального робота** (`q_real = q_sim`). Yaw базы в обеих сценах
  `airy_table_scene14sep26_left_image[_metric]` повёрнут на −85.98° (50.593° → −35.387°): ось joint0 совпадает
  с осью Z базы, поэтому это то же самое, что прибавить 85.98° к joint0, но теперь без пересчёта. Значение
  измерено проверкой зависания (ICP ладони по глубине ZED): снимок в стартовой позе показывал ~90°, зависание
  дало поправку −4.02°. Предел joint3 в URDF расширен до ±360°, как у реального робота (старт joint3 = +179.52°).
- **Смещение joint0 скрипт определяет сам** по yaw базы, с которым записана траектория: для новых записей 0°,
  для записанных до поворота базы — +85.98°. Строка `j0 offset` в dry-run показывает значение и источник;
  `--j0-offset` задаёт его явно (с предупреждением, если оно расходится с вычисленным).
- **Возвращайтесь из зависания через `--reverse`**, а не `--move-to-start`: путь к зависанию идёт
  через подъём на безопасную высоту, а одно суставное движение этот подъём срезает и может провести
  кисть низко рядом с объектом.
- **Развёртка на 360°**: траектория каждого сустава сдвигается на кратное 360° к фактическому
  углу робота. Иначе, например, joint3 −180.5° в симуляторе против +180.0° на роботе
  провернулся бы на полный оборот.
- **Yaw базы известен с точностью около градуса** (метод ICP даёт ~1 см), и реальная кисть идёт на ~1 см ниже плана.
  Поэтому первый прогон — зависание (`--until-height`), затем проверка выравнивания.
- Перед движением скрипт ждёт ENTER; Ctrl+C — робот в hold, кисть раскрывается. Если робот
  дальше `--start-tol-deg` от старта, нужен явный `--move-to-start`.

## Декартов реплей дельт (`replay_npz_real.py`)


```bash
# Dry-run: только статистика, без железа. ВСЕГДА запускать первым.
python3 replay_npz_real.py ../runs/manual/pick_up_green_cube_ext_20260907_095442 --dry-run

# На реальном роботе
python3 replay_npz_real.py ../runs/manual/pick_up_green_cube_ext_20260907_095442

# Медленнее
python3 replay_npz_real.py <run_dir> --speed 0.3
```

Принимает как директорию прогона (найдёт `rl4vla_raw_episode*.npz`, предпочитая `_success`),
так и путь к самому `.npz`.

Ctrl+C в любой момент → E-stop (робот в hold, кисть открывается).

## Отличия формата от JSONL

| | JSONL (teleop) | NPZ (ManiSkill) |
|---|---|---|
| Поза | `abs_pose` — абсолютная | только дельты EE |
| Время | `t` в записи | шаги × control_freq (20 Гц) |
| Кисть | 7 углов на каждый кадр | один тернарный канал: hold / open / close |
| Кадр | фрейм реального робота | фрейм базы симулятора |

Соответственно:

- **Абсолютные позы восстанавливаются интегрированием дельт** от позы робота на старте
  (или от `--start-pose`). В отличие от JSONL-реплея, здесь есть накопление ошибки.
- **Кисть**: при запуске по папке траектории поза пальцев читается из `runtime_config.yaml`
  этой папки (при запуске по прямому пути к `.npz` — из встроенной копии конфига).
  Подробнее ниже.
- **Ремапа фрейма нет.** Дельты применяются в том виде, в каком записаны. Dry-run печатает
  суммарное смещение (`Net XYZ delta`) в исходном фрейме эпизода — сверьте с реальной
  ячейкой до запуска на железе.

## Положения пальцев AeroHand

`AeroHand.set_joint_positions()` принимает **углы суставов в градусах** и сам внутри
прогоняет модель сухожилий (`JointsToActuationsModel`), пересчитывая их в 7 актуаторов.
Поэтому в скрипте ничего пересчитывать не нужно и нельзя — иначе конверсия произойдёт
дважды.

Короткая форма из 7 значений разворачивается SDK в 16 суставов так:

```
[0] thumb_cmc_abd   [1] thumb_cmc_flex   [2] thumb_mcp = thumb_ip
[3] index x3        [4] middle x3        [5] ring x3        [6] pinky x3
```

| состояние | константа | значение | пределы |
|---|---|---|---|
| HOLD (и OPEN) | `HAND_HOLD` | `[70, 3.5, 14, 37.4, 29.4, 30.2, 29.4]` | 100, 55, 90, 90, 90, 90, 90 |
| CLOSE | `HAND_CLOSE` | `[100, 55, 30, 60, 60, 60, 60]` | — |

`HAND_HOLD` — профиль `side` из `robot_init_qpos` (та поза, что проверялась на рендере
кисти), углы переведены из радиан в градусы. Отведение большого пальца снижено со 100°
(предел сустава, как в профиле) до **70°** — на реальной кисти при 100° он выпирает
слишком сильно. У этого профиля все три фаланги
каждого пальца имеют одинаковый угол, поэтому он точно ложится в форму из 7 значений.

Профиль `top` в 7 значений **не сводится** (mcp/pip/dip различаются) — для него нужна
форма из 16, `set_joint_positions` её тоже принимает:

```
[44.94, 8.58, 11.22, 20.05, 20.26, 25.15, 25.06, 15.25,
 30.14, 20.05, 15.25, 30.15, 20.05, 1.81, 40.17, 20.06]
```

При старте скрипт проверяет, что `HAND_HOLD` не выходит за суставные пределы.

## Важное ограничение: дельты — это цели, а не пройденный путь

Control mode эпизодов — `arm_pd_ee_target_delta_pose_align2_gripper_pd_joint_pos`,
то есть `use_target=True`: каждая дельта прибавляется к *целевой* позе замкнутого контура,
а не к достигнутой. Планировщик в симуляции — тоже замкнутый P-контроллер: пока рука
отстаёт, он продолжает выдавать дельты. В результате **сумма дельт заметно больше
фактического перемещения**.

Замер на `pick_up_green_cube_ext_20260907_095442`:

| Стадия | Команда (сумма дельт) | Факт в симуляции | Превышение |
|---|---|---|---|
| Спуск | 23.3 см | 21.2 см | ×1.1 |
| Подъём | 25.2 см | 9.5 см | **×2.6** |

Скрипт считает это расхождение в dry-run и печатает предупреждение. Открытый реплей
дельт проедет дальше, чем ездила симуляция — особенно на подъёме.

Аккуратный способ это закрыть — экспортировать из симуляции абсолютные позы TCP по шагам
и реплеить их (как `abs_pose` в JSONL-варианте). Сейчас в NPZ их нет.
